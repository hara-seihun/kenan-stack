# Peer Kenaznia channel

Lets a person's Kenaznia message another Kenaznia (on another host, or another person's on this host), and receive its messages in its live conversation.

- **Config**: each person in `/etc/kenan/CHANNEL.json` has `peers: [{id, name, about}]` (`[]` for none). A person with peers must have their Kenaznia hosted on that channel. `id` is this side's name for the other Kenaznia.
- **Agents**: people with peers get the `peer` tool: `send` queues a message in `peer_message` (direction `out`), `history` lists both directions with `relayedAt`.
- **Socket**: `/run/kenan/CHANNEL-peer/PERSON.sock` (owned by the person's unix user, 0600): `GET /outbox?peer=ID&wait=S` long-polls unrelayed messages, `POST /ack {peer, ids}` marks them relayed, `POST /inbox {id, peer, from, to?, text, createdAt}` stores an inbound message once per id and delivers it as a `note` input (joins its current turn) plus a notice in its conversation to `to` (an agent id on this side) while that agent is live, otherwise to the manager. The `peer` tool's optional `to` sets it on outbound messages, and every delivered note names the sender's agent id to reply `to`, so a worker talking to the other side gets the replies itself. Source: `server/peers.ts`, regression `server/peers.test.ts` (two databases, two sockets and the real relay).
- **Relay**: `peer-relay.mjs CONFIG.json` runs both directions; the remote side is reached through a command prefix (`["ssh", "acme-host"]`). Delivery is at-least-once to the socket and exactly-once to the agent (inbound ids are unique). Config field `alertUid` (required) names whose phone hears about a stall: when either direction has failed for 10 minutes the relay queues one `Peer relay stalled` notification through `kenan-notify --uid` (naming the failing direction, its last error and any waiting messages), and one `Peer relay recovered` once both directions work again. Required `alertFile` (e.g. `/var/lib/machine-alerts/inbox/peer-relay-acme.md`) holds the same stall as a machine condition, with both sides' `kenan@CHANNEL` unit state, until it recovers; Kenaznia's heartbeat lists it. Restarting a stopped channel is the host's `kenan-runtime-recovery` timer's job (enabled channels restart; `systemctl disable` holds one stopped on purpose), never the relay's. On 2026-10-19 acme-host's Kenan was down 21:15–23:47Z and five messages sat unrelayed unnoticed. Install for the current user with `deploy/peer/install.sh NAME CONFIG.json`; logs in `journalctl --user -u kenan-peer-relay@NAME`. Two people on this host: `deploy/peer/install.sh --host NAME CONFIG.json` runs `kenan-peer-relay-host@NAME` as root (it reaches both people's sockets) with the config in `/etc/kenan/peer-relay/NAME.json`; logs in `journalctl -u kenan-peer-relay-host@NAME`.
