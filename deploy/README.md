# Kenan rewrite deployment

The application has one process and database per channel, ordinary home directories, and separate built application directories. Each person's personal folder is the plain directory `HOME/ACCOUNT_ID` (for example `/home/kenan/alice`).

First preparation as root from the checkout:

```sh
bash deploy/prepare.sh
```

Each channel creates its schema (`server/db/schema.sql`) in its own database at first start. Every deploy, frontend or backend, uses the same command:

```sh
deploy/deploy.sh beta
deploy/deploy.sh production
```

Each command builds the commit as the checkout's owner with `deploy/prepare-build.sh` into `GIT_DIR/kenan-deploy/builds/COMMIT`, whose `node_modules` links to `GIT_DIR/kenan-deploy/deps/LOCKFILE_SHA256` (one `npm ci` per lockfile). Both are assembled in private temporary directories and published by rename, so Beta and production deploy the same checkout in parallel with no lock and no shared mutable tree, the second channel reuses the first's build (0.02 s), a fresh clone deploys directly, and the checkout's own `node_modules`/`dist` are never touched. Keys unused for three days are pruned. Host files both channels write (units, `/usr/local/{bin,sbin}` tools, mail CLI releases, the Acme backup payload) are placed by rename through `deploy/place.sh` (`place`, `place_link`, `place_tree`), because uutils `install` fails one of two concurrent writers with `install: Already exists`. It then stages all files while the app stays online. Frontend-only updates publish the new assets and index without restarting the backend or its event streams. Backend or dependency changes stop the channel only for the prepared file swap, then start it once. Dependencies are recopied only when the lockfile changes. Per-channel publication is serialized. Old hashed web assets remain available to open tabs. The command checks the accounts endpoint. Several agents deploy in parallel, so a deploy must contain the commit the channel already runs (`/srv/kenan/CHANNEL/source-commit`). `deploy/lineage.sh` refuses, before building or detaching, with `deploy_would_drop_live_commits` listing the live commits the checkout lacks; merge or rebase onto them and deploy again. It also refuses uncommitted changes (`deploy_uncommitted_changes`), a HEAD that is on no branch of the shared `origin` (`deploy_commit_unpublished`; push first so the next deployer can include it) and a live commit absent from both the checkout and origin (`deploy_live_commit_unknown`). `install-build.sh` re-reads the live commit under the channel lock and refuses with `deploy_channel_moved` if another deploy landed during the build. Roll back by deploying the previous commit from a checkout of it with `deploy/deploy.sh CHANNEL --rollback`, which prints the commits it removes.

Services: `kenan-postgres.service`, `kenan@beta.service`, `kenan@production.service`. Config: `/etc/kenan/CHANNEL.json`; data: `/var/lib/kenan/CHANNEL`; builds: `/srv/kenan/CHANNEL`; PostgreSQL socket: `/run/kenan/pg`. `kenan-entrance@CHANNEL.service` is the nginx listener (`/etc/kenan/entrance-CHANNEL.conf`, from `deploy/`; Beta `127.0.0.2:18190`, production on the tailnet address) that the mesh entrance proxies to. `kenan-model-broker.service` runs the subscription broker from `/srv/kenan/broker/current` with `/etc/kenan/model-broker.json`; `kenan-port-access.service` (`deploy/port-access.py`) reserves each broker port for root, `kenan` and that listener's person, and the ports in `/etc/kenan/owner-ports.json` (code-server, adb) for root and `kenan`. Its ledger is `/var/lib/kenan/model-broker/ledger.sqlite3`. Per-person tool configuration is `/etc/kenan/domains/ACCOUNT.json`, the shared catalog `/etc/kenan/shared-model-pool.json`, login verifiers `/etc/kenan/verifiers`, browser/Chrome binaries `/srv/kenan/toolchains`. `deploy/install-browser.sh install BINARY SOURCE_COMMIT` installs an agent-browser release build (from `cli/target/release/agent-browser` of example-owner/agent-browser) as `/srv/kenan/toolchains/browser-SRC8-SHA8` and selects it for every `/etc/kenan/domains/*.json` and the owner's `~/.local/bin/agent-browser`; `select DIR` rolls back to an earlier toolchain and `current` prints the selected one. Running browser daemons restart on their next command because the daemon identity includes the source commit. Provider/browser/mail state is in `/var/lib/kenan/account-state`. `deploy/prepare.sh` installs all these units.

## Compute priority

Heavy agent work must never starve the apps, the broker, calls or the household's own services. Every owner process (Bash, file tools, mail, browser; `ownerProcess` in `server/tools/owner.ts`) runs in its own transient scope `agent-tool-CHANNEL-UUID.scope` inside the owner's `user-UID.slice` at CPU/IO weight 10, bound to `kenan@CHANNEL.service` without ordering after it (a restart still ends it, concurrently, so a tool process stuck in the kernel cannot hold the service stop; `TimeoutStopSec=10s` bounds such a scope), dropped to the owner with no supplementary groups through `setpriv`, with `OOMPolicy=continue`. When the kernel OOM-kills anything in that scope, the tool output ends with a `[kenan] The kernel OOM killer killed …` line naming the process and the exhausted budget (gated on `user.slice`'s `memory.events`, details from the kernel log).

Weights (`deploy/priority/`, mirrors `/etc/systemd/system`): `system.slice` 400 against `user.slice` 100; inside `system.slice`, `system-kenan.slice` (the apps), the broker, PostgreSQL, the entrances and `kenan-call-*` phone bridges are 1000 with `MemoryLow`, `kenan-backup.service` 10 and nice 10. Inside `user.slice` each person's `user-UID.slice` keeps weight 100 and `MemoryLow=512M`, so their own services outrank their agents' weight-10 tool scopes; `user-1000.slice` (kenan, the agent administrator account, whose user units are all agent research) and `user@1000.service` are weight 10. `user.slice` is one memory budget (`MemoryHigh=40G`, `MemoryMax=44G`, `MemorySwapMax=0`), so a runaway job is throttled, then OOM-killed inside it instead of swapping the host. Background swap is disabled: even a 4 GB allowance produced prolonged memory reclaim and shared-disk contention during simultaneous model conversions (October 20). `deploy/priority-user/service.d` (mirrors `/etc/systemd/user`) makes every user service killed for memory print a `[kenan] UNIT was killed by the kernel OOM killer` line into its own output. `prepare.sh` installs both trees; `systemctl daemon-reload` (and `systemctl --user -M USER@ daemon-reload`) applies them to running units without restarts. `deploy/priority-check.sh` is the regression check: it saturates every core from an agent-tool scope and measures app, broker and phone-websocket latency against an idle baseline.

`bench/latency.ts` measures admission in a disposable archived room without invoking models. Credentials are read from a file rather than command arguments. Full tests: `npm test`; on a host with `/run/kenan/pg` the database suites use its `kenan_test` database (set `KENAN_TEST_DATABASE_URL` to choose another).

PostgreSQL uses the existing encrypted B2 pgBackRest repository with its own `kenan` stanza and the existing two-full-backup retention. `kenan-backup.timer` runs hourly; WAL archiving runs continuously. Configuration lives in `/etc/kenan/pgbackrest.conf`; restart `kenan-postgres.service` before starting the apps, run `sudo -u postgres pgbackrest --config=/etc/kenan/pgbackrest.conf --stanza=kenan check`, then `systemctl enable --now kenan-backup.timer` and `systemctl start kenan-backup.service`. `kenan-wal-guard.timer` (`deploy/wal-guard.py`) suspends archiving before unarchived WAL can fill the disk and resumes it once the repository answers. Restic retains ordinary homes, sessions and files, and excludes live PGDATA because pgBackRest owns consistent database recovery.

Release a native change with `android/release.sh CHANNEL` from a checkout whose `android/` is committed: it takes the next version code from the live manifest, builds and unit-tests, stages, signs, installs and publishes. Run long builds under `systemd-run --user` so a Kenan restart doesn't kill them. The app installs updates itself; from version 47 on, Android skips the consent prompt for its self-updates. Signed native updates live at `/var/lib/kenan/android/CHANNEL`: `manifest.json`, `manifest.sig`, `signer.der` and the SHA-named APK. `android/stage.mjs` owns staging and `server/http/android.ts` serves `/api/android/release`, `/api/android/update`, `/api/device/android-update`, `/api/android/apk/SHA.apk` and `/app.apk`. Copy verified final build contents from `/var/lib/kenan/android-build/CHANNEL/android/` before channel activation; the build scratch directory is disposable afterward.

Each successful hourly database backup is followed by its files/sessions/native-artifacts/account-state snapshot in the existing B2 restic repository, tagged `kenan-files` with the original two-snapshot retention. The last observed file snapshot is recorded at `/var/lib/kenan/backup/files-snapshot.json`. Retention is scoped to that tag and leaves other backup tags unchanged.

The outer mesh entrance serves native updates from its `/var/lib/kenan/android-channels/CHANNEL` static alias. `deploy/publish-android.mjs` mirrors the verified signed build there during deployment, atomically updates the existing channel symlink, and retains older content-addressed APKs for in-flight downloads.

## Developer contributions

Alice gave Robin the same Kenan Stack development access she has (2026-10-14). `deploy/contribute.py` is installed as `/usr/local/bin/kenan-stack-contribute`, with the registry `/etc/kenan/developers.json`, the exact sudo grant `deploy/contribute.sudoers` (run as `kenan`) and the queue `/var/lib/kenan/contributions`.

A developer streams `git bundle create - BRANCH | sudo -n -u kenan kenan-stack-contribute check|submit BRANCH FULL_SHA`. The commit must descend from `/srv/kenan/beta/source-commit`. `submit` stores it as `refs/heads/contrib/DEVELOPER/BRANCH` and queues an entry. Alice's agents merge the queued entries, deploy Beta, and then close each one with `kenan-stack-contribute settle ID published BETA_SOURCE_COMMIT` or `settle ID rejected REASON`. `kenan-stack-contribute status` lists the queue. Entries touching `deploy/`, `patches/` or `package*.json` are flagged, because deployment runs them as root.

`deploy/deploy.sh` re-executes itself through `sudo -n` when not run as root. Deployments requested from inside an app service are dispatched to an independent transient systemd unit before building or stopping anything. This prevents the app shutdown from killing its own deployment. The command returns the unit name; inspect completion with `sudo journalctl -u UNIT.service` (agent processes lack the journal group). If the detached deploy fails, it queues a phone notification with the exit status and the log tail for the requesting unix user's person with `deploy/kenan-notify`. The same guard applies to direct `install-build.sh` calls.

## Organized layout

Enable it for a person by adding `"organized"` (and `"rooms"` for Kenaznia's rooms tool) to their `extensions` in `/etc/kenan/CHANNEL.json` and restarting the channel; on that start their to-do list is seeded once from `HOME/ID/memory/todo.md` if they have none. They then choose Classic or Organized in the ☰ menu (DESIGN.md, Organized layout).

## Adding a person

`sudo kenan-add-person ID NAME --pronouns PRONOUNS|none --like TEMPLATE [--mesh-key]` (source `deploy/add-person.py`, installed to `/usr/local/sbin` by every forward deploy) does the whole enrollment on kenan-server, each step only when missing: Unix account (next free UID from 1006) and personal folder, `/etc/kenan/users/ID/AGENTS.md` linked from the home, account state and `/etc/kenan/domains/ID.json` copied from TEMPLATE, login secret `/etc/kenan/provision/ID.login-key` with its verifier, a model-broker listener (the broker restarts without blocking; agents retry meanwhile), entries in both channel configs with Kenaznia hosted on production, the deny ACL on Alice's private tree, port reservations, the Headscale user and, with `--mesh-key`, a single-use 7-day pre-auth key in `/etc/kenan/provision/ID.mesh-key`. It restarts production and fails unless a real login with the new secret succeeds; Beta picks the person up at its next restart. It prints paths, never secrets.

## Host phone notifications

Host services notify a person's phone through a durable outbox: `/var/lib/kenan/notify/PERSON/`, owned by that person's unix user (mode 0700, created by the channel hosting their manager). `kenan-notify [--uid UID] TITLE normal|urgent < BODY` (installed to `/usr/local/bin` by every forward deploy; source `deploy/kenan-notify`) writes one JSON file `{title, body, level, image?: {mime: image/jpeg|png|webp, base64}}` there atomically; other producers may write the same JSON themselves as a dot-named temp file renamed to `NAME.json` (names sort in delivery order; `$(date +%s%N)-…` works). The server (`server/notify-outbox.ts`) delivers it like the agent `notify` tool, attributed to the person's manager, and deletes it; a file that isn't a valid notification becomes `NAME.invalid` with an `error_log` row (`notify_outbox`). A file written while Kenan is stopped or restarting waits and is delivered when the channel starts, so no alert is lost to a restart; regression `server/notify-outbox.test.ts`.

## Host events (wake agents from host scripts)

`kenan-event [--uid UID] [--id ID] TOPIC < JSON` (installed to `/usr/local/bin` by every forward deploy; source `deploy/kenan-event`) queues one event in `/var/lib/kenan/events/PERSON/` (owned by the person's unix user, mode 0700, created by the channel hosting their manager) as `{"topic", "id", "body"}`; other producers may write that JSON themselves as a dot-named temp file renamed to `NAME.json`. TOPIC is 1–200 of `A-Z a-z 0-9 . _ : @ / -`; the body is any JSON value up to 256 KiB; `--id` is an idempotency key (the person records an id once; default a random UUID). The channel records it (`server/event-inbox.ts`; invalid files become `NAME.invalid` with an `error_log` row `event_inbox`) and fires that person's agents' `wake` with `on: "event"` and a matching `topic` (exact, or a prefix ending in `*`) at once, carrying the body. An event that arrives before the wake is scheduled waits (14 days) for the first matching wake. Agents learn their id from their prompt; by convention a host script addresses one agent as `SOURCE:<agent id>`. Regression `server/event-inbox.test.ts`.

**Acme event relay** (`deploy/event-relay/`): `kenan-event-relay@acme` (user unit of `kenan`, lingering; config `~/.config/kenan-event-relay/acme.json`, script `/usr/local/lib/kenan/event-relay/event-relay.mjs`, logs `journalctl --user -u kenan-event-relay@acme`) holds one long-lived `ssh -o ControlMaster=no -o ControlPath=none -o ServerAliveInterval=30 acme-host` session running `tail -F /home/kenan/data/acme-releases/events.jsonl`, reconnecting with backoff (1 s to 60 s) and resuming after the byte offset of the last forwarded line (`~/.local/state/kenan-event-relay/acme.json`). Each line that is a JSON object with a string `owner` becomes `kenan-event --id acme:<sha256 of the line> acme:<owner>` with the line's object as body; other lines are logged and skipped. SIGTERM/SIGINT stop it gracefully: the line in flight is forwarded and its offset saved before it exits, so a restart re-offers nothing; only a crash between forwarding and saving re-offers that line, under the same id, which the inbox records once. A session down 10 minutes sends one `Event relay acme stalled` phone alert through `kenan-notify`, and one on recovery. Install or update: `deploy/event-relay/install.sh acme CONFIG.json`. Regression `deploy/event-relay/event-relay.test.ts`.
