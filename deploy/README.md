# Kenan rewrite deployment

The application has one process and database per channel, ordinary home directories, and separate built application directories. Each person's personal folder is the plain directory `HOME/ACCOUNT_ID` (for example `/home/kenan/alice`).

First preparation as root from the checkout:

```sh
bash deploy/prepare.sh
```

Each channel creates its schema (`server/db/schema.sql`) in its own database at first start. Every change, frontend or backend, goes to Beta first, and production only ever gets the commit live on Beta:

```sh
deploy/deploy.sh beta     # new code, from a clean pushed checkout
deploy/promote.sh         # production gets exactly /srv/kenan/beta/source-commit
```

`deploy/promote.sh` takes no arguments: it checks out Beta's live commit in a per-user clone (`~/.local/state/kenan-promote`) and runs `deploy/deploy.sh production` there, so it works the same for administrators and for household operators going through `kenan-operator`. `deploy/lineage.sh` refuses a forward production deploy of any other commit with `deploy_production_not_beta` (exit 9), whichever route called it; `deploy/deploy.sh production` from a checkout already at Beta's commit is the same promotion. A host without the requested channel config returns `deploy_channel_not_configured` (exit 10) before preparing source or detaching; promotion does not create a production channel on a Beta-only host. Promotion invokes `deploy.sh production --wait`, which waits for the detached systemd unit and returns its exit status immediately on failure. After production successfully runs Beta's commit (else `promote_production_not_live`, exit 12) or when production already ran it, promote runs `deploy/bundle-acme.sh COMMIT`. `COMMIT` accepts Git commit references such as `HEAD`, branch names and tags, resolved in `KENAN_BUNDLE_REPO` (default `/home/kenan/work/repos/kenan.git`) before bundling. Invalid references return `bundle_commit_invalid`; missing full commit IDs return `bundle_commit_unknown`. On the account with the Acme peer relay, it creates a complete git bundle in `~/.local/state/kenan-acme-bundles/` and copies only that bundle to `/var/tmp/kenan-stack-COMMIT.bundle` on acme-host over SSH. Acme's timer automatically picks up the newest bundle, qualifies it and deploys it; its own alert covers failed intake. Normal promotions write no peer message. Only when Acme needs a decision (host configuration, migration or breaking change), set `KENAN_BUNDLE_NOTE="Decision needed: …" deploy/promote.sh` or run `deploy/bundle-acme.sh COMMIT --note "Decision needed: …"` (`--note` overrides the environment). The requested note is queued atomically in `/var/lib/kenan/peer-outbox/alice/`, survives restarts, and uses a stable per-commit message id. Copy or requested-note queue failures raise `deploy:manager:alice:acme-bundle` and return nonzero with production already live; rerun promotion to finish the copy or note. Accounts without that relay skip it; household operators use the installed helper as kenan. Promotion never changes Acme's source or deploys there. See [Acme source exchange](README-acme.md#source-exchange-with-acme). `--rollback` still replaces production with any pushed commit deliberately. A host with no `/srv/kenan/beta` deploys production directly (regression in `deploy/lineage.test.ts`).

On the account that exports to Acme, a successful forward Beta deploy and every bundle export start `deploy/background-check.mjs` independently in a systemd user service. It runs `npm run check` and `npm test -- --project suites --changed BASE --passWithNoTests` on a private copy of the released source, using the previous export as BASE (or the previous live Beta commit before the first export). Neither command gates a deployment or bundle copy. Results and logs live in `~/.local/state/kenan-background-checks/COMMIT/`; repeated triggers reuse the running or completed check. The log includes Vitest's ordinary error summary, and `runner-errors.json` retains errors outside assertions (which Vitest's JSON reporter omits). These errors also appear in `result.json` failures; an otherwise unexplained nonzero exit names the test process and log. Each exported bundle has a same-stem JSON manifest with the background check's status and `skippedDatabaseSuites` (null while not yet known, an explicit list once complete), plus all skipped tests. The manifest is updated remotely when the check finishes. Each atomic upload uses its own temporary file; an initial status can never overwrite a completed result. Only the ordinary suites project runs; timing suites are outside this feedback check.

A failed check queues `goal-0918c2aa-86f8-47ba-a2eb-4b723fafc31c:fixture-check` through the existing durable host-event inbox. The fixture repair goal holds an event wake for this topic, so only its repair owner resumes, without firing Kenaznia's unrelated personal wakes. The repair worker should: compare the assertion with the intentional interface change, update only stale fixtures without weakening behavior assertions, check that behavior once, and publish the fix in the next export. A real behavior break goes to the change's author instead. No snapshot replacement or expected-value rewriting runs blindly. Start/copy failures also queue a repair event, without changing a successful deploy/export into a failure. The hook is skipped on accounts without the Acme relay configuration.

When `kenan-public-github.service` is installed, successful Beta deploys on hosts without `/etc/kenan/production.json` start public source publication asynchronously. Two-channel hosts keep publication after production promotion through `deploy/promote.sh`. Both use `deploy/public-github/trigger.sh`; hosts without the service skip publication. The daily timer remains independent.

Move a person's Kenaznia, history and files between channels with `deploy/move-person.py PERSON FROM TO TARGET_URL` as root, from a detached unit (it stops both channels for about a minute); `--check` rehearses the copy in a rolled-back transaction while both keep running, and rerunning an interrupted move copies the rows again. Operators move themselves with `sudo kenan-operator move-self FROM TO [--check]`.

Each command builds the commit as the checkout's owner with `deploy/prepare-build.sh` into `OWNER_HOME/.cache/kenan-deploy/builds/COMMIT`, whose `node_modules` links to `OWNER_HOME/.cache/kenan-deploy/deps/LOCKFILE_AND_PATCHES_SHA256` (one `npm ci` per dependency key). The account database supplies `OWNER_HOME` from the executing uid, not inherited `HOME`: ordinary worktrees, separate clones and the promotion clone share finished keys for the same owner, while different owners use separate caches. This also preserves dependency mtimes across checkouts, avoiding unnecessary phone-edge dependency transfers. Existing per-checkout caches and serving trees are not changed. Regression `deploy/prepare-build.test.ts` exercises distinct worktrees and a promotion clone. A caller that sets an absolute `KENAN_BUILD_CACHE` (Acme points it at a qualified, pre-seeded cache) has it used instead of the account cache: every hop between `deploy.sh` and `prepare-build.sh` starts from a clean environment (the `sudo` re-exec as root, the detached `systemd-run` unit, the `sudo` to the owner), so each hands it over explicitly (`--preserve-env=PATH,KENAN_BUILD_CACHE`, `--setenv=KENAN_BUILD_CACHE=…`, `env KENAN_BUILD_CACHE=…`), and an empty or relative value is refused with `build_cache_not_absolute` before the first hop (regression `deploy/build-as-owner.test.ts`). The `kenan-operator` route builds as root from its own checkout and deliberately takes no caller cache. Both are assembled in private temporary directories and published by rename, so Beta and production deploy the same checkout in parallel with no lock and no shared mutable tree, the second channel reuses the first's build (0.02 s), a fresh clone deploys directly, and the checkout's own `node_modules`/`dist` are never touched. Keys unused for three days are pruned. Host files both channels write (units, `/usr/local/{bin,sbin}` tools, mail CLI releases, the Acme backup payload) are placed by rename through `deploy/place.sh` (`place`, `place_link`, `place_tree`), because uutils `install` fails one of two concurrent writers with `install: Already exists`. It then stages all files while the app stays online. Frontend-only updates publish the new assets and index without restarting the backend or its event streams. Backend or dependency changes stop the channel only for the prepared file swap, then start it once. Dependencies are recopied only when the lockfile changes. Per-channel publication is serialized. Old hashed web assets remain available to open tabs. The command checks the accounts endpoint. Several agents deploy in parallel, so a deploy must contain the commit the channel already runs (`/srv/kenan/CHANNEL/source-commit`). `deploy/lineage.sh` refuses, before building or detaching, with `deploy_would_drop_live_commits` listing the live commits the checkout lacks; merge or rebase onto them and deploy again. It also refuses uncommitted changes (`deploy_uncommitted_changes`), a HEAD that is on no branch of the shared `origin` (`deploy_commit_unpublished`; push first so the next deployer can include it) and a live commit absent from both the checkout and origin (`deploy_live_commit_unknown`). `install-build.sh` re-reads the live commit under the channel lock. Forward deploys accept a concurrent live commit already included in the prepared build; otherwise they refuse with `deploy_channel_moved` so the missing commit can be merged. Explicit rollbacks still require the live commit to match the version checked before building, so a concurrent deploy is never silently rolled back. Roll back by deploying the previous commit from a checkout of it with `deploy/deploy.sh CHANNEL --rollback`, which prints the commits it removes.

Services: `kenan-postgres.service`, `kenan@beta.service`, `kenan@production.service`. Config: `/etc/kenan/CHANNEL.json`; data: `/var/lib/kenan/CHANNEL`; builds: `/srv/kenan/CHANNEL`; PostgreSQL socket: `/run/kenan/pg`. `kenan-entrance@CHANNEL.service` is the nginx listener (`/etc/kenan/entrance-CHANNEL.conf`, from `deploy/`; Beta `127.0.0.2:18190`, production on the tailnet address) that the mesh entrance proxies to. `kenan-model-broker.service` runs the subscription broker from `/srv/kenan/broker/current` with `/etc/kenan/model-broker.json`; `kenan-port-access.service` (`deploy/port-access.py`) reserves each broker port for root, `kenan` and that listener's person, and the ports in `/etc/kenan/owner-ports.json` (code-server, adb) for root and `kenan`. Its ledger is `/var/lib/kenan/model-broker/ledger.sqlite3`. Per-person tool configuration is `/etc/kenan/domains/ACCOUNT.json`, the shared catalog `/etc/kenan/shared-model-pool.json`, login verifiers `/etc/kenan/verifiers`, browser/Chrome binaries `/srv/kenan/toolchains`. `deploy/install-browser.sh install BINARY SOURCE_COMMIT` installs an agent-browser release build (from `cli/target/release/agent-browser` of alice-Example/agent-browser) as `/srv/kenan/toolchains/browser-SRC8-SHA8` and selects it for every `/etc/kenan/domains/*.json` and the owner's `~/.local/bin/agent-browser`; the shared `/usr/local/bin/agent-browser` follows that owner link, so shared PATH callers use the same selected build. `select DIR` rolls back to an earlier toolchain and `current` prints the selected one. Running browser daemons survive CLI releases. The CLI reports an older build without restarting it; explicitly close that session or use a new session name to use the installed build. Conflicting settings on an older daemon return an error without losing tabs. Headless Chrome never outlives what launched it: `deploy/priority-user/agent-browser-.service.d` runs every agent-browser daemon with no session bus, so Chrome can't move itself into its own `app-org.chromium.Chromium-PID.scope` and stops with the daemon however the daemon ends (idle timeout, `close`, crash, `kill -9`); the same drop-in sets `AGENT_BROWSER_IDLE_TIMEOUT_MS=1800000`, so a daemon whose agent didn't set its own idle timeout (Erin's and Dave's didn't; 25 h idle ones piled up on 2026-11-01) exits after 30 minutes without a command; `kenan-chrome-reap.timer` (`deploy/chrome-reap.py`, as root every 5 minutes) stops any other headless Chrome with a DevTools port or pipe whose launcher has gone (parent is init or a systemd user manager), for scripts and runners that don't use agent-browser. Regression check: `python3 deploy/chrome-reap.test.py`. Provider/browser/mail state is in `/var/lib/kenan/account-state`. `deploy/prepare.sh` installs all these units.

## Build dependencies

Run `bash deploy/install-build-deps.sh` before building or installing source dependencies. On Debian/Ubuntu it installs missing `build-essential` (GCC, G++, make and libc headers), `pkg-config`, `libjson-c-dev`, `libsystemd-dev`, `libnode-dev` (the background helper’s N-API headers), `python3` and `git`. The helper selects `libsystemd-dev` at the installed native `libsystemd0` version so backports installations keep matching headers and libraries. Install Node.js >=24 with npm separately; the helper never replaces an existing Node installation. It checks headers and links the native libraries before any application build. On other distributions or without root/passwordless sudo, it fails with the missing package names. `--check` reports without installing.

Fresh preparation, deployment, prepared builds, forward installation, broker/background installers, `npm ci` and `npm run build` all call this same helper. Independent updaters should run it as root from the new source **before** running `npm ci` as the application owner. The npm hooks also protect direct source builds; an unprivileged updater gets an early, actionable error rather than a failure after TypeScript compilation.

## Live code and configuration upgrades

Backend deploys and `sudo /usr/local/sbin/kenan-runtime-restart beta` load the selected release into the running Node process. `systemctl reload kenan@beta` uses the same control socket. HTTP handlers change immediately; running Pi sessions, model streams, tool calls, queues and SSE subscribers remain alive. A finished turn hands its next batch to the new runtime and rebuilds its session there. Startup interruption recovery is only for an actual process exit, not a deployment.

`server/main.ts` is the small permanent loader; `live-generation.ts` starts and upgrades the application. `live-modules.ts` reuses unchanged module graphs, including singleton state. Runtime state is shared explicitly in `agents/runtime.ts`; `live-store.ts` preserves the store identity while existing operations finish against their old implementation. Changed extension services keep one owner: `live-extensions.ts` waits for their in-flight calls, switches the service, and sends subsequent calls to its new implementation. Other background intake is stopped and reopened without stopping agent execution.

`install-build.sh` selects immutable backend code in `/srv/kenan/CHANNEL/releases/COMMIT` and dependencies in `dependencies/KEY`; old modules and binaries remain available to running turns. Shared web assets and commit history keep their existing paths. The first installation over a version without live upgrades replaces the process once. A changed database address, listening address or data directory returns `live_reload_address_changed`; replacing that service is a separate operation. A failed live reload does not fall back to killing running turns. `kenan-runtime-restart CHANNEL --replace` deliberately replaces a process through the independent system-manager unit; use it only for bootstrap or host/listening/database changes. Ordinary code/configuration upgrades never use this option.

## Startup

Unchanged schema startup reads the PostgreSQL catalog before creating or altering its bookkeeping table. An `ALTER TABLE ... IF NOT EXISTS` still takes an exclusive table lock and must not run when the column is already present: a database dump holds read locks until it finishes. Startup logs include each extension's duration and the elapsed time to listening.

## Schema upgrade proof

Before a build with a `server/db/schema.sql` change is installed over a serving one, `DB=URL deploy/schema-proof/schema-catalog-proof.sh REPO BASE HEAD OUT_DIR` proves the upgrade in throwaway schemas of a test database (assistant-host: `postgresql:///kenan_test?host=/run/kenan/pg&user=$USER`), applying each commit's schema.sql exactly as `store.migrate` does. The fresh BASE vs fresh HEAD catalog difference must equal the exact allowlist `deploy/schema-proof/delta.py allow` derives from the BASE..HEAD schema.sql diff (every differing catalog line is named by a changed line; every added column or index shows up), so nothing is listed by hand. Rows from `deploy/schema-proof/seed.sql` (every baseline table) are fingerprinted across BASE→HEAD (equals fresh HEAD), HEAD applied twice, a BASE start on the upgraded database with values written into every HEAD-only column, HEAD again, fresh HEAD→BASE→HEAD, and a stale pre-baseline database that must be refused with `schema_predates_baseline` and left unchanged (`GUARD_REMOVED=1` turns those red). Exit 0 PASS, 1 a named check failed, 2 setup error; it drops every schema it created.

## Meeting voice transcripts

GPT Live input and output transcript deltas are retained in the owner-scoped `kenan_meeting_voice_transcript` table, including their provider, voice-session, event, ordering and timestamp identities. They survive a voice reconnect or server restart; the in-memory 20,000-character agent context is not the durable record. Owner-only `meeting inspect` includes the latest 2,000 pieces as `modelTranscript` for both native and Recall sessions. Older pieces remain in the table. This is model text, not proof of audible speech. Raw transcripts are not added to shared meeting notes or Insight. Storage errors enter the normal error log without gating speech or meeting controls. Rolling back the application leaves the transcript table and its evidence intact.

## Dictation runtime

When dictation is enabled, `deploy/dictation-models.sh CHANNEL BUILD` installs whisper.cpp, ffmpeg and the local models before the app starts. Fresh-host installers and independent update commands should call it as root too; building the app alone does not install those host dependencies.

Dictation selects the multilingual base model automatically when whisper.cpp reports no Vulkan compute device, with CPU inference and at most four threads (never more than the available CPUs). Hosts with a usable Vulkan device keep Turbo, Vulkan and up to eight threads. A virtual display render node alone does not select GPU inference. The short engine retains its 15.36-second audio context; the full engine accepts longer clips. Only GPU engines run synthetic warm-up for pipeline compilation; CPU engines start ready for real audio.

## Mail dispatch concurrency

Mail's send wrapper serializes only matching request IDs. A bare `to: "mail"` means a reply, not one shared thread;
independent replies run together. The CLI retains request and recipient/thread locks and durable success replay.
Other outbound channels still serialize their addresses.

## Mail attachments

Mail wake startup checks the installed `mail-search --help` for `position` and bounded `search --after`; an incompatible CLI reports `mail_cli_incompatible` with the installation command. Each folder watch and each wake evaluation has its own outage and retry state. A successful watch or another wake cannot clear a failing evaluation; its error is reported after five minutes.

`deploy/install-mail.sh install` installs the shared mail CLIs. `prepare.sh` installs them on a fresh host; `install-build.sh` selects them from the prepared build before every forward publication, including direct callers. Rollbacks keep the newer shared CLIs. `prepare-build.sh` only builds source and never changes installed tools. Independent installers and updaters (including `kenan-update`) must run `sh "$SOURCE/deploy/install-mail.sh" install` as root from the new source before replacing the app, including frontend-only updates. `mail-send` identifies JPEG, PNG, GIF, WebP, BMP, TIFF and PDF attachments by content signature. It appends a matching extension to extensionless or uninformatively named files in the outgoing message, preserving the supplied name and leaving the original file untouched. Matching filename extensions stay unchanged. Conflicting types fail with `attachment-type-mismatch` before sending; other formats use filename-based MIME detection. A draft prints each outgoing attachment's filename, type and size without sending or printing its bytes.

## Compute priority

Heavy agent work must never starve the apps, the broker, calls or the household's own services. Ordinary owner processes (Bash, file tools, mail, browser; `ownerProcess` in `server/tools/owner.ts`) run in its own transient scope `agent-tool-CHANNEL-UUID.scope` inside `user-agents.slice`, shared by every person's agent commands, at CPU/IO weight 100, with `TimeoutStopSec=10s` and `MemoryLow=64M` protecting a small command's working set from bulk-job reclaim without increasing the shared hard cap. Bash logs are created as the owner before launching, so even a pre-start failure has a readable full-output file (empty when nothing ran or printed). A launcher stopped by the startup watchdog reports a launch timeout, not an unexplained external signal. Bash scopes are independent of `kenan@CHANNEL.service`, so a deploy does not end their computation; other owner-process scopes remain bound to it without ordering after it, dropped to the owner with no supplementary groups through `setpriv`, with `OOMPolicy=continue`. When the kernel OOM-kills anything in that scope, the tool output ends with a `[kenan] The kernel OOM killer killed …` line naming the process and the exhausted budget (gated on `user.slice`'s `memory.events`, details from the kernel log).

On ResearchCo, agent commands and background jobs run directly without CPU quotas. Each foreground tool scope and background service has a 32 GiB hard memory limit and no swap; a runaway allocation fails its own job instead of stalling every shell. The drop-ins are `priority/agent-tool-.scope.d/60-job-memory.conf` and `priority/kenan-bg-.service.d/60-job-memory.conf`. The shared user.slice hard limit is whole GiB of physical RAM minus 16 GiB reserved for system services and another 16 GiB for kernel/CMA and other host work (93 GiB here). Aggregate MemoryHigh is disabled: it makes small command launches reclaim other jobs' pages and can stall every agent's shell despite available physical RAM. Aggregate swap is capped at 8 GiB. systemd-oomd monitors user.slice and kills a reclaiming descendant job when full memory pressure exceeds 10% for five seconds, avoiding minutes of shared reclaim before kernel OOM. The application services and emergency recovery command are outside that slice and keep their reserved memory, elevated CPU weight and lower OOM score. `sudo oomctl dump` shows monitored groups; `journalctl -u systemd-oomd` names killed jobs. `install-local-policy.sh`, called by preparation and every forward deploy, installs and applies this policy; Acme keeps its own host-specific limits. The kernel OOM notice names the affected command; reduce its memory use and retry.

When shared job memory prevents Bash startup, its built-in `kenan-recover status` command reads memory pressure and the owner's largest processes. `kenan-recover kill PID` stops one selected process owned by that Unix user inside user.slice, using a pidfd so a reused PID is never signalled. These fixed operations run as the owner in a separate system.slice scope with a 128 MiB memory cap, one CPU, 16 tasks and a 15-second lifetime. They cannot execute arbitrary shell text or move research work outside its shared cap. Implementation: `server/tools/recovery.ts` and `server/tools/owner.ts`.


`bench/latency.ts` measures admission in a disposable archived room without invoking models. Credentials are read from a file rather than command arguments. Full tests: `npm test`, or `npm test -- PATHS` for selected files. All files run serially. Ordinary database suites use `/run/kenan/pg`'s `kenan_test` database when available (`KENAN_TEST_DATABASE_URL` overrides it). The timing project always starts its own socket-only PostgreSQL process on the runner's cores: the shared host database is excluded from benchmark cores, so giving only Node dedicated CPUs did not isolate admission timing. Local PostgreSQL server binaries are required, found through `pg_config --bindir` or `TEST_POSTGRES_BIN`; missing binaries fail rather than skip the latency tests. The timing cluster keeps normal durability; only the benchmark admission sessions disable synchronous commit, while its concurrent writers explicitly keep durable commits.

PostgreSQL uses the host's encrypted B2 pgBackRest repository; WAL archiving runs continuously. On ResearchCo, `/etc/kenan/pgbackrest-ResearchCo.conf`, stanza `ResearchCo`, and `ResearchCo-pgbackrest.service` own full backups. `kenan-wal-guard.timer` (`deploy/wal-guard.py`) checks every five minutes and discovers `data_directory` from local SQL, including host-specific PostgreSQL unit overrides. Before enabling it, write root-owned `/etc/kenan/wal-guard.json` with explicit host policy (no credentials):

```json
{
  "socket": "/run/kenan/pg",
  "pgbackrestConfig": "/etc/kenan/pgbackrest-ResearchCo.conf",
  "stanza": "ResearchCo",
  "fullBackupService": "ResearchCo-pgbackrest.service"
}
```

`deploy/install-wal-guard.py` validates the policy before installing the helper. Preparation requires it; normal forward deploys call it through `install-local-policy.sh` on every host that already has the guard or its policy, before any ResearchCo-only settings. Hosts without the guard are left alone. When policy is missing, the installer can convert the existing `/etc/kenan/backup.json` repository config and stanza only if they match the live SQL archive command and exactly one installed direct pgBackRest `--type=full backup` service. The old Stack SQL socket `/run/kenan/pg` is used for this conversion unless the existing policy specifies `socket`. A suspended, mismatched or ambiguous installation fails with a named error; write explicit local policy rather than guessing. Existing explicit policy is preserved and its selected full-backup command is checked against its repository and stanza.

Other hosts must select their own repository and full-backup unit; the service must take a fresh full backup on each start. Acme's scheduled service switches between full and incremental backups, so it needs a dedicated direct full-backup service for guard recovery. The installer does not change other hosts, service enablement or masks. The guard saves the active archive command in root-only `/var/lib/kenan/wal-guard.json` before suspending archiving to prevent a full disk. Once the selected stanza answers `pgbackrest info`, it restores that exact command and queues the policy's full-backup service. An interrupted recovery remains pending until systemd accepts the backup. For a suspension created before command-saving was installed, it reconstructs `pgbackrest --config=POLICY_CONFIG --stanza=POLICY_STANZA archive-push %p`. Restic retains ordinary homes, sessions and files, and excludes live PGDATA because pgBackRest owns consistent database recovery.

Release a native change with `android/release.sh CHANNEL` from a checkout whose `android/` is committed: it takes the next version code from the live manifest, builds, stages, signs and publishes. The release build fails when Android lint finds a platform API (NewApi) or inlined constant (InlinedApi) newer than `minSdk` without an `SDK_INT` guard or `@RequiresApi`: `lintVitalRelease` runs inside `assembleRelease` with both checks fatal (`android/app/build.gradle.kts`), because an unguarded Android 14 call once crashed the app on open on Android 13. Check native changes on an Android 13 (API 33) emulator before releasing. Run long builds under `systemd-run --user` so a Kenan restart doesn't kill them. The app installs updates itself; after initial Android consent and installer ownership, its self-updates do not need another prompt. Signed native updates live at `/var/lib/kenan/android/CHANNEL`: `manifest.json`, `manifest.sig`, `signer.der` and the SHA-named APK. `android/stage.mjs` owns staging and `server/http/android.ts` serves `/api/android/release`, `/api/android/update`, `/api/device/android-update`, `/api/android/apk/SHA.apk` and `/app.apk`. Copy verified final build contents from `/var/lib/kenan/android-build/CHANNEL/android/` before channel activation; the build scratch directory is disposable afterward.

Each successful hourly database backup is followed by its files/sessions/native-artifacts/account-state snapshot in the existing B2 restic repository, tagged `kenan-files` with the original two-snapshot retention. The hourly run only forgets old snapshots; the weekly `restic-system-maintenance` prunes the shared repository (an hourly `--prune` repacked the whole repository every hour and ran into the 2026-10-22 02:00Z memory thrash). The last observed file snapshot is recorded at `/var/lib/kenan/backup/files-snapshot.json`. Retention is scoped to that tag and leaves other backup tags unchanged.

The outer mesh entrance serves native updates from its `/var/lib/kenan/android-channels/CHANNEL` static alias. `deploy/publish-android.mjs` mirrors the verified signed build there during deployment, atomically updates the existing channel symlink, and retains older content-addressed APKs for in-flight downloads.

## Developer contributions

Alice gave Robin the same Kenan Stack development access she has (2026-10-14). `deploy/contribute.py` is installed as `/usr/local/bin/kenan-stack-contribute`, with the registry `/etc/kenan/developers.json`, the exact sudo grant `deploy/contribute.sudoers` (run as `kenan`) and the queue `/var/lib/kenan/contributions`.

A developer streams `git bundle create - BRANCH | sudo -n -u kenan kenan-stack-contribute check|submit BRANCH FULL_SHA`. The file-based deployment entrypoints (`deploy.sh`, `promote.sh`, `install-build.sh` and `bundle-acme.sh`) disconnect stdin before running children, so an SSH-fed `bash -s` keeps reading its remaining commands. Their inputs are arguments and environment variables; streaming configuration and secret handoffs keep their own stdin.

`deploy/deploy.sh` re-executes itself through `sudo -n` when not run as root. Deployments requested from inside an app service are dispatched to an independent transient systemd unit before building or stopping anything. This prevents the app shutdown from killing its own deployment. The command returns the unit name; `--wait` instead returns when that independent unit finishes, with its exit status. Inspect completion with `sudo journalctl -u UNIT.service` (agent processes lack the journal group). If the detached deploy fails, it queues a phone notification with the exit status and the log tail for the requesting unix user's person with `deploy/kenan-notify`. Both `prepare.sh` and every deploy call it. Independent installers and `kenan-update` commands must run `bash "$SOURCE/deploy/install-runtime-control.sh"` as root after writing their channel config and before starting or replacing the app; it changes no app code, credentials or host-specific service settings. Bash refuses inline control of its own local runtime and directs callers to `kenan-runtime-restart`. It reads SSH destinations and shell command boundaries, so remote restarts are allowed while local commands before or after SSH, local expansions, and SSH client commands remain checked.

## Host events (wake agents from host scripts)

`kenan-event [--uid UID] [--id ID] TOPIC < JSON` (installed to `/usr/local/bin` by every forward deploy; source `deploy/kenan-event`) queues one event in `/var/lib/kenan/events/PERSON/` (owned by the person's unix user, mode 0700, created by the channel hosting their manager) as `{"topic", "id", "body"}`; other producers may write that JSON themselves as a dot-named temp file renamed to `NAME.json`. TOPIC is 1–200 of `A-Z a-z 0-9 . _ : @ / -`; the body is any JSON value up to 256 KiB; `--id` is an idempotency key (the person records an id once; default a random UUID). The channel records it (`server/event-inbox.ts`; invalid files become `NAME.invalid` with an `error_log` row `event_inbox`) and fires that person's agents' `wake` with `on: "event"` and a matching `topic` (exact, or a prefix ending in `*`) at once, carrying the body. An event that arrives before the wake is scheduled waits (14 days) for the first matching wake. Agents learn their id from their prompt; by convention a host script addresses one agent as `SOURCE:<agent id>`. Regression `server/event-inbox.test.ts`.

**Acme event relay** (`deploy/event-relay/`): `kenan-event-relay@acme` (user unit of `kenan`, lingering; config `~/.config/kenan-event-relay/acme.json`, script `/usr/local/lib/kenan/event-relay/event-relay.mjs`, logs `journalctl --user -u kenan-event-relay@acme`) holds one long-lived `ssh -o ControlMaster=no -o ControlPath=none -o ServerAliveInterval=30 acme-host` session running `tail -F /home/kenan/data/acme-releases/events.jsonl`, reconnecting with backoff (1 s to 60 s) and resuming after the byte offset of the last forwarded line (`~/.local/state/kenan-event-relay/acme.json`). Each line that is a JSON object with a string `owner` becomes `kenan-event --id acme:<sha256 of the line> acme:<owner>` with the line's object as body; other lines are logged and skipped. SIGTERM/SIGINT stop it gracefully: the line in flight is forwarded and its offset saved before it exits, so a restart re-offers nothing; only a crash between forwarding and saving re-offers that line, under the same id, which the inbox records once. A session down 10 minutes sends one `Event relay acme stalled` phone alert through `kenan-notify`, and one on recovery. Install or update: `deploy/event-relay/install.sh acme CONFIG.json`. Regression `deploy/event-relay/event-relay.test.ts`.

### Background jobs and heavy work
Foreground Bash is restart-safe by default (`server/tools/foreground.ts`). Its independent native runner (`foreground-runner.c`) uses inotify, timerfd and signalfd for completion, cancellation and deadlines without starting a JavaScript runtime per command. The runner registers its transient scope directly over systemd D-Bus, waits for the start job, then drops to the owner UID/GID and supplementary groups before reading the job. This avoids starting systemd-run, setpriv and a wrapper shell for each call. Scope identity and limits come from the app, not the owner-writable job file. The build compiles it beside the server module; `install-build-deps.sh` checks and installs the shared build dependencies before a deployment builds. The resource scope, owner identity and persisted job/result files stay the same. File notifications deliver completed output immediately instead of a 100 ms completion poll; a one-second watchdog covers unavailable or missed notifications. Notifications stop following live output after the display limit, while the original log and final tail remain available. Its independent scope retains native call identity and the existing resource limits, with `RuntimeMaxSec` bounding a separate 60-second startup allowance, the command timeout, and five seconds for shutdown. The command timeout begins when the runner starts, not while systemd is launching it. A delayed runner reads cancellation before executing the command; startup failures cannot execute later. A small runner writes output to `/var/tmp/USER/bash-output/foreground-UUID.log` (the existing 12-hour tmpfiles cleanup) and an atomic result beside its pending command in `HOME/.local/state/kenan/foreground/CHANNEL/AGENT/`. The restarting app detaches, while explicit Stop, archive, preemption and timeout cancel the command. Live output is bounded to its first 50 KiB and the completed result to its last 50 KiB; omitted bytes stay in the original log, whose path is included, rather than being copied through Pi after the command ends. Before that agent’s next model call, the runtime waits for only its own outstanding commands and adds saved output and exit status, redacted, to the prompt. It never reruns them. Pending descriptions are removed as soon as Pi persists either the real tool result or the recovery prompt; a shutdown-generated abort result does not count. On session load, outstanding descriptions are reconciled against the complete journal (including this agent's trimmed transcripts) before trimming or recovery, so compaction never makes delivered output appear outstanding. A runner that exits without saving a result produces an explicit error, including its output log. A missing result after its deadline requests cancellation and stops only that call's scope, then reads any final result before returning an unknown-outcome error. Jobs started by the previous runner retain their original deadline during deployment. Tests: `server/tools/foreground.test.ts` and `server/agents/runtime-provider.test.ts`.

`kenan-bg NAME [--env VARIABLE]... -- CMD` runs a command in the background and raises an event when it ends; it does not admit heavy work by itself. It checks that the command exists before creating a log or detaching, and returns `bg_executable_missing` otherwise. CPU work runs directly on ResearchCo. Acme uses `acme-heavy-slot reserve/launch` layered on `acme-host-slot`, and the Bash tool describes that route there. Its job event carries `outcome` (`success`|`failed`|`oom`). Regressions `deploy/kenan-bg.test.py`, `server/tools/owner.test.ts`.

`kenan-image` (source `deploy/kenan-image/`, guide `SKILL.md` installed to `/usr/local/share/kenan/skills/image/`) makes cartoon and sketch images for every person's agents at no cost: SD-Turbo on the CPU, one step, about 10–15 s per 512 px image, then optional tracing to SVG (vtracer), cut-out layers and layered SVGs for dress-up games. Every forward deploy runs `deploy/install-image-gen.sh`, which is idempotent: a Python 3.12 environment built from the pinned `requirements.txt` (torch from the CPU-only wheel index, so it never uses the iGPU that dictation needs) in `/opt/kenan-image-<hash>` behind the `/opt/kenan-image` symlink, the weights pinned by revision and sha256 in `model.txt` in `/var/lib/kenan/models/image/sd-turbo`, and the host-wide lock `/var/lib/kenan/image-gen/lock`. Each `gen` holds that lock (one image job on the host; others wait up to 4 minutes, then get `busy`) and runs one short process under `chrt --idle` and `nice 19`, so it only uses CPU nobody else wants: during a benchmark dictation latency stayed within noise of idle, where three plain cores at nice 15 slowed the large Whisper model by 60–80%. Nothing stays running between calls. The bash tool text names it when it is on PATH (`hostToolsText`, `server/tools/owner.ts`).

Basic process settings and exports added or changed from the calling tool’s original environment are inherited automatically (see `kenan-bg --help`), including `GRK_K=4 GR_NORETRY=1 kenan-bg fit -- python3 x.py` and exports made in nested shells. The launcher compares against the initial environments of the calling tool’s process chain, not the login profile or just the immediate parent. Unchanged unrelated exports remain excluded; select one with `--env VARIABLE`. Missing or unexported requested names fail before detachment. If the original environment cannot be read, `bg_env_baseline_unavailable` names the exports to select explicitly instead of silently dropping them. Selected values travel through stdin/the launch socket and the `systemd-run` process environment, never its arguments or launch logs; do not put secrets in the command itself or print them in the job. Name matching is exact, including one-letter variables. Retry identity includes the selected environment, so a changed value is a different invocation.

Native status gets systemd state, the owner's saved log, terminal outcome and last 20 log lines (at most 64 KiB) in one authenticated socket response. It never searches other agents' logs or repeats the systemd query. Launch request construction selects the exported environment in the same JSON encoding pass.

Native `kenan-bg stop NAME` returns `state: "already-inactive"` and `stopRequested: false` if no live job remains, rather than claiming it stopped the job. For live work it returns `stopped` (no job processes remain) or `stopping` (survivors listed). `stopRequested` records an accepted systemd stop or a successful signal; `liveProcessesFound` records whether live job processes were observed. These fields do not claim that the stop caused the exit. The response includes the owner's saved `log`, known `exitCode`, `outcome` and `endedAt`, and `priorOutcome` (the terminal result known before stopping, or null). Completed units are not stopped again; only leftover job processes are stopped. Missing systemd state returns an error, not a successful stop. Owner checks apply to both saved launches and loaded units. Stopping keeps the existing bounded escalation and adds no waiting.

Native worker jobs stop automatically after their worker is archived or stopped. `kenan-bg-reap.timer` checks once a minute, queries the owning channel’s configured database in one batch, and uses the existing whole-job stop (including escaped child scopes). Each stopped job gets a plain reason in its log. Jobs watched by a pending wake or held trigger keep running, including exact/prefix topic matches from any local channel and an owner’s handed-off `on: "any"` wait. Missing owner rows, failed database reads and manager-owned jobs are left alone. `kenan-bg --keep NAME -- CMD` explicitly keeps a job running after its owner ends; this choice is retained in the root-created unit and launch record.

`bash deploy/install-background.sh` installs only the background CLI and its launch socket (`kenan-bg-launch.socket`), without an application build or restart. Native UUID workers launch through the warm root `kenan-bg-launch.service` in system.slice. Its small N-API credential reader gets the connected peer's PID, UID and GID from `SO_PEERCRED`; four warm worker threads run the shared `background-launch.mjs` authentication and launch code. Concurrent requests get an idle thread or an additional thread immediately, without a shared request queue; extra threads exit after a minute idle. The installer builds the credential reader with `gcc` and `libnode-dev` when its source changes, and drains/restarts the launcher when its code changes; only `socat` runs in the caller's often CPU-starved tool scope (a missing socket or refused connection uses the same helper under sudo; an established connection with a lost reply never submits a fallback): stopped sockets remove their pathname, and installing changed socket settings restarts the listener. A verified current native scope creates a root-managed transient service running as the original Unix user. Its root-created launch description retains the exact native worker, channel and originating tool call after detachment. Raw inherited tool IDs are still stripped. The native observer requires matching current control group, user, active transient unit and invocation metadata; user-manager lookalikes never authenticate. Non-native jobs retain their existing user-manager route.
Completion events keep the full log path and terminal status. Successful jobs include at most eight nonblank final output lines, capped at 1 KiB; failed, stopped and OOM jobs include up to 8 KiB of head/tail diagnostics. A successful job still resumes its worker when no wake was scheduled; Kenaznia carries unwatched successes with its next wake.

## ResearchCo post approval

Alice's `todos` extension runs a local HTTP service at `dataDir/ResearchCo-post.sock` (0600, Alice's Unix owner). `POST /proposals` accepts `{proposal, chatId?, test?}`; the proposal has `source_file`, `title`, `posts` (exact platform, destination, text, link, image path/alt and optional video), and `media` (absolute path, sha256 and size). Errors are `{ok:false,error:{code,message}}`. Test proposals can be reviewed but can never be claimed or auto-published.

Only Alice's cookie-authenticated client route `POST /api/ext/todos/post-proposals/ID/decision` with `{choice:"Yes"|"No"|"Edit"}` records a signed decision. Original media bytes are checked again before Yes and on every claim. A replacement for the same `source_file` supersedes earlier unclaimed proposals. Yes starts the fixed `ResearchCo-post publish ID` program in an independent system unit; an approved action not yet claimed is started again after a server restart. Private test servers never start the real publisher. Program-start errors enter the normal error log. The publisher owns safe retry records and its resulting platform URLs under ResearchCo's posts folder.

This prevents accidental agent use; it does not prove human presence against a trusted administrator or an agent using Alice's authenticated browser/session. State, media copies and the decision key belong in the existing encrypted app backups. Tool and post operations: `/home/kenan/tools/ResearchCo-post/README.md`.
